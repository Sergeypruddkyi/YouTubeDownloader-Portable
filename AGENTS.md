## 0.1. Приоритет решений

При выполнении задачи использовать следующий порядок:

1. последнее явное указание пользователя в текущей сессии;
2. текущий `AGENTS.md`;
3. фактическое состояние исходников и Git текущего проекта;
4. предыдущие отчёты / handoff только как вспомогательный контекст.

Если документация, handoff или предположение противоречат фактическому состоянию текущего проекта — не додумывать и не восстанавливать состояние самостоятельно. Сначала показать конкретное противоречие.

Не переносить решения, пути, архитектуру или команды из других проектов только потому, что они там работали.

## 0.2. Последовательность задач и checkpoint

Задачи выполняются последовательно и только в пределах назначенной задачи.

Агент не должен самостоятельно:

- перескакивать к следующей задаче;
- добавлять «заодно» следующие функции;
- начинать крупный рефакторинг, не требуемый текущей задачей;
- продолжать работу после достижения оговорённого checkpoint без нового указания;
- превращать одну задачу в длинную цепочку скрытых дополнительных задач.

Один логический блок работы — одна задача или чётко ограниченная часть задачи.

После существенного блока агент должен остановиться и сообщить:

- что сделано;
- какие файлы изменены;
- что проверено;
- build/test result;
- что осталось;
- можно ли переходить к следующему шагу.

Если задача не прошла — не маскировать проблему заглушкой и не переходить дальше.

`commit` и `push` не выполнять без явного указания пользователя. Это правило имеет приоритет над любыми шаблонами из других проектов.

## 0.3. Observable Result / вертикальный прогресс

Приоритет разработки — работающий и проверяемый продукт, а не накопление невидимой инфраструктуры.

Предпочтительный цикл:

```text
изменение
→ build / publish
→ запуск актуального EXE из dist
→ реальный результат
→ ручная проверка
→ checkpoint
→ следующий шаг
```

`dotnet build` PASS сам по себе не считается пользовательским результатом.

Unit-тесты PASS сами по себе не считаются пользовательским результатом, если задача требует проверки UI или реального поведения.

По возможности каждый этап должен как можно быстрее приводить к результату, который пользователь может:

- запустить;
- увидеть;
- проверить;
- использовать.

Инфраструктурная работа допустима только если она действительно необходима для ближайшего рабочего результата. Агент должен понимать и уметь сообщить:

1. зачем она нужна;
2. какой ближайший результат она разблокирует;
3. после какой конкретной задачи этот результат можно будет проверить.

Не создавать дополнительные слои, абстракции и «заделы на будущее» без необходимости текущей задачи.

## 0.4. Проверка фактического checkpoint

Предыдущий отчёт, handoff или сообщение агента не заменяют проверку фактического состояния репозитория.

Если заявленный checkpoint не совпадает с тем, что видно в текущем проекте:

1. не считать работу потерянной;
2. не начинать проект заново;
3. не делать автоматически `checkout`, `switch`, `reset`, `clean`, `merge`, `rebase`;
4. выполнить только безопасную read-only диагностику Git;
5. показать пользователю фактическое состояние;
6. дождаться разрешения на изменяющее состояние действие.

Безопасные диагностические команды:

```text
git status
git branch -a
git log --all --oneline --decorate
git show <commit>
git diff
git reflog
```

Если нужный commit находится в другой ветке — сначала сообщить пользователю. Не переключаться автоматически.

Эти правила обязательны для всех агентов, работающих в
`E:\Projects\YouTubeDownloader-Net10`. Они фиксируют реальный порядок работы
проекта, чтобы никогда не повторялась ситуация, когда агент тестирует одну
сборку (в `bin\...\publish`), а пользователь запускает другую, старую сборку из
`dist`.

## 1. Канонический production/test output

Рабочий portable output проекта:

```
E:\Projects\YouTubeDownloader-Net10\dist\YouTubeDownloader\
```

Именно этот каталог является **каноническим артефактом приложения** для:

- ручного запуска;
- визуального тестирования;
- UI Automation;
- проверки реального поведения приложения;
- checkpoint / release-подготовки.

Любая проверка «как у пользователя» выполняется только из этого каталога.

## 2. Publish

Production publish должен формировать актуальную сборку непосредственно в:

```
dist\YouTubeDownloader
```

Это уже настроено в проекте: `src\YouTubeDownloader.csproj` задаёт `PublishDir`,
указывающий на `..\dist\YouTubeDownloader\`, поэтому команда

```
dotnet publish -c Release -r win-x64 --self-contained true
```

кладёт .NET-артефакты сразу в канонический `dist`.

После изменения исходного кода агент **НЕ** должен считать тестирование в

```
src\bin\Release\net10.0-windows\win-x64\publish\
```

достаточным, если пользователь в дальнейшем запускает `dist`.

Если `bin\...\publish` существует как промежуточный output, он **не** является
каноническим пользовательским/тестовым артефактом.

## 3. Обязательная проверка

После изменения кода и publish агент обязан проверять именно:

```
dist\YouTubeDownloader\YouTubeDownloader.exe
```

и соответствующую ему:

```
dist\YouTubeDownloader\YouTubeDownloader.dll
```

Нельзя отчитываться «UI проверен» только на основании запуска другой копии EXE
из `bin\publish`.

## 4. Синхронность EXE/DLL

В обычном .NET publish apphost `YouTubeDownloader.exe` — это лишь launcher, а код
приложения находится в `YouTubeDownloader.dll`. Наличие или отсутствие функции
(например кнопки в Editor) определяется **DLL**, а не самим EXE.

Поэтому при диагностике рассинхронизации нужно проверять:

- EXE;
- соседнюю DLL;
- дату/время последнего изменения;
- при необходимости SHA256.

EXE и DLL в `dist` должны относиться к одной и той же свежей publish-сборке.
Признак несоответствия — разные даты/время или разные SHA256 между тем, что
собрано, и тем, что лежит в `dist`.

## 5. External runtime / sidecar files

В `dist` также находятся внешние runtime-файлы, которые **не** являются
результатом обычной .NET сборки. На текущем checkpoint сохранены:

- `ffmpeg.exe` 9.0.1
- `ffprobe.exe` 9.0.1
- `deno.exe` 2.9.7
- `yt.exe` 2026.08.19

Также могут присутствовать:

- `settings.ini`;
- другие необходимые portable / runtime-файлы.

При publish **нельзя** бездумно очищать весь `dist` и удалять эти файлы.
`dotnet publish` по умолчанию не удаляет посторонние файлы в выходном каталоге,
поэтому обычный publish в `dist` безопасен; опасны ручная очистка каталога и
флаги вроде явного clean по всему `dist`.

Нужно всегда различать:

- .NET publish output (управляемые DLL/EXE, `*.deps.json`, `*.runtimeconfig.json`,
  системные `System.*.dll`, `clr*.dll` и т. п.);
- внешние portable runtime / sidecar-файлы (ffmpeg, ffprobe, deno, yt, settings.ini).

После publish проверять, что версии внешних бинарников не откатились:

```
ffmpeg  -version    # 9.0.1
ffprobe -version    # 9.0.1
deno    --version   # 2.9.7
yt.exe  --version   # 2026.08.19
```

## 7. Тестирование

После существенных изменений production build проверяется из канонического
`dist`. Минимально:

```
dist\YouTubeDownloader\YouTubeDownloader.exe --selftest
```

и, если изменения затрагивают Editor:

```
dist\YouTubeDownloader\YouTubeDownloader.exe --editortest Test.mp4
```

Для UI Automation использовать именно EXE из `dist\YouTubeDownloader`.

Для `--editortest` в `dist` должен присутствовать `Test.mp4`. Это тестовый ресурс;
если его нет, его можно временно положить рядом, но он не является частью
приложения.

## 8. Git checkpoint

Git checkpoint относится не только к исходному коду, но и к реально проверенному
рабочему состоянию portable-приложения. Перед checkpoint нужно убедиться, что
одной проверенной версии соответствуют:

- source code;
- EXE/DLL в `dist`;
- необходимые изменённые runtime-артефакты.

Не делать `commit` / `push` без явного указания пользователя.

## 9. Обязательное правило после изменений

Правильная последовательность:

```
изменение source
  → build / publish
  → обновление dist
  → запуск EXE из dist
  → тестирование (--selftest / --editortest)
  → визуальная / UI проверка
  → отчёт
```

Неправильно:

```
изменение source
  → тестирование случайного EXE из bin\publish
  → пользователь запускает старый EXE из dist
```

## 11. Окружение сборки (обязательно)

В оболочке агента переменные окружения Windows урезаны. Если запускать
`dotnet build` / `dotnet publish` «как есть», NuGet падает ещё до компиляции:

```
error : Value cannot be null. (Parameter 'path1')
```

Причина — пустые `PROGRAMDATA`, `APPDATA`, `CommonProgramFiles` и т. п., из-за
чего NuGet не может определить machine-wide конфигурацию. Это НЕ ошибка проекта.

Перед любой сборкой/публикацией выставлять окружение, например:

```bash
export PROGRAMDATA='C:\ProgramData' ALLUSERSPROFILE='C:\ProgramData' \
       APPDATA='C:\Users\Rulman_PC\AppData\Roaming' \
       LOCALAPPDATA='C:\Users\Rulman_PC\AppData\Local' \
       windir='C:\WINDOWS' SystemRoot='C:\WINDOWS' SystemDrive='C:' \
       CommonProgramFiles='C:\Program Files\Common Files' \
       ProgramFiles='C:\Program Files'
dotnet build -c Release
```

Работает только полный набор: без `CommonProgramFiles`/`ProgramFiles` ошибка
воспроизводится. Проверка окружения без сборки:

```
dotnet nuget locals all --list
```

## 12. UI Automation

Готовый harness для проверки редактора на реальном EXE из `dist`:

```
tools\uia_cut_check.py
```

Запуск (нужен интерактивный рабочий стол и 12-минутный тестовый ролик):

```
C:\Users\Rulman_PC\.workbuddy-ai\binaries\python\envs\default\Scripts\python.exe tools\uia_cut_check.py
```

Скрипт сам открывает редактор через реальные клики, зумит таймлайн
(Ctrl+колесо) до «весь клип в окне», ставит playhead настоящей мышью (SendInput)
и читает статус-строку через UIA. Отчёт пишется в `uia_cut_report.txt`.

Полезно знать про этот WinForms-провайдер UIA:

- кнопки ищутся по имени, но поиск иногда не отвечает — нужен обход дерева
  (`WalkTree` + `GetChildren`) и повторные попытки;
- `GetDescendants()` в пакете `uiautomation` отсутствует;
- метки (`Label`) безоконные: искать их надо как `TextControl(searchDepth=1)`,
  а не через перебор детей окна;
- дерево доступности наполняется не сразу после запуска: давать паузу ~3 с.
